\chapter{پیاده‌سازی}

در پیاده‌سازی، مهم‌ترین نکته این است که کاربر از بیرون چه رفتاری می‌بیند و پشت آن رفتار، چه بخش‌هایی با هم کار می‌کنند. به همین دلیل، متن به جای تکیه بر نام فایل‌ها و مسیرهای داخلی، مسیرهای اصلی محصول را توضیح می‌دهد: از کاتالوگ و ورود گرفته تا \lr{Dashboard}، انتشار \lr{API}، \lr{Caller}، \lr{Studio} و تحلیل و استقرار پروژه.

\section{مسیرهای بک‌اند}
بک‌اند مجموعه‌ای از مسیرهای نسخه‌دار دارد که بخش‌های اصلی محصول را پوشش می‌دهند: سلامت سامانه، قرارداد \lr{OpenAPI}، ثبت‌نام، ورود، خروج، حساب کاربری، پروفایل، \lr{API Key}، سازمان‌ها، اشتراک، مصرف، کاتالوگ، مستندات، \lr{Endpoint}ها، \lr{Caller}، \lr{Studio}، تولید پروژه، تحلیل آرشیو و صف استقرار. نسخه‌دار بودن مسیرها کمک می‌کند توسعه آینده کنترل‌شده‌تر باشد و \lr{Client}ها با تغییرات ناگهانی روبه‌رو نشوند \cite{drf,openapi}.

این مسیرها دو سطح تجربه می‌سازند. سطح اول عمومی است و برای مشاهده کاتالوگ، جزئیات \lr{API} و مستندات استفاده می‌شود. سطح دوم خصوصی است و بعد از ورود کاربر فعال می‌شود؛ مثل \lr{Dashboard}، مصرف، اشتراک، سازمان و انتشار \lr{API}. همین جداسازی باعث می‌شود کاربر مهمان با داده خصوصی روبه‌رو نشود و توسعه‌دهنده بعد از ورود، فضای کاری خودش را ببیند.

\section{لایه \lr{Repository}}
لایه \lr{Repository} منطق کار با داده را متمرکز می‌کند. ساخت کاربر، نگهداری نشست، چرخش \lr{API Key}، خواندن کاتالوگ، ثبت مصرف \lr{Caller}، ذخیره جریان‌های \lr{Studio} و مدیریت رکوردهای پروژه و استقرار از همین مسیر انجام می‌شود. این شیوه باعث می‌شود \lr{View}ها بیش از حد شلوغ نشوند و جزئیات داده در یک لایه مشخص بماند.

در پروژه‌ای شبیه بازارچه \lr{API}، این جداسازی اهمیت زیادی دارد. داده‌های حساب، کاتالوگ، مستندات، اشتراک و مصرف شکل یکسانی ندارند. وقتی این بخش‌ها پشت یک \lr{Repository} قرار می‌گیرند، تغییر در روش ذخیره‌سازی کمتر به بخش‌های دیگر نشت می‌کند.

\section{\lr{Serializer} و قرارداد پاسخ}
\lr{Serializer}ها مرز امن بین داده داخلی و خروجی قابل نمایش هستند. داده‌ای که داخل سامانه نگهداری می‌شود، همیشه نباید با همان شکل به کاربر برگردد. برای نمونه، مقدار کامل \lr{API Key} نباید در پاسخ عادی دیده شود و بهتر است فقط نسخه پنهان‌شده آن نمایش داده شود. این رویکرد با نقش \lr{Serializer} در \lr{Django REST Framework} هماهنگ است \cite{drf}.

در بخش انتشار \lr{API} نیز \lr{Serializer} کمک می‌کند داده ورودی قبل از ثبت بررسی شود: نام، آدرس پایه، روش احراز هویت، دسته و توضیح سرویس باید روشن باشند. نتیجه این کار، پاسخ‌هایی است که برای فرانت‌اند قابل پیش‌بینی‌تر و برای کاربر قابل فهم‌ترند.

\section{فرانت‌اند}
فرانت‌اند همان جایی است که کاربر بیشترین تماس را با محصول دارد: صفحه مرور \lr{API}ها، جزئیات سرویس، مستندات، قیمت‌گذاری، پرداخت، ورود، ثبت‌نام، \lr{Dashboard}، سازمان‌ها، انتشار، \lr{Caller}، \lr{Studio}، تولید اسکلت پروژه و ابزار تحلیل و استقرار. معماری کامپوننتی \lr{React} برای چنین تجربه‌ای مناسب است، چون بخش‌های تکرارشونده مثل فرم، کارت، جدول و وضعیت بارگذاری را می‌توان جدا نگه داشت \cite{react}.

ارتباط فرانت‌اند با بک‌اند از طریق \lr{Client}های مشخص انجام می‌شود. یک گروه درخواست‌ها برای کاتالوگ است، یک گروه برای احراز هویت، و یک گروه برای حساب کاربری و ابزارهای توسعه‌دهنده. این جداسازی باعث می‌شود صفحه‌ها کمتر به جزئیات آدرس‌ها وابسته باشند و نگهداری پروژه ساده‌تر شود.

\section{نمونه کد}
نمونه زیر بخش کوچکی از منطق پنهان‌کردن داده حساس را نشان می‌دهد.
\begin{latin}
\begin{lstlisting}[language=Python]
SENSITIVE_KEYS = {"password", "api_key", "token", "secret", "authorization"}

def redact_secrets(value):
    if isinstance(value, dict):
        return {
            key: "[REDACTED]" if str(key).lower() in SENSITIVE_KEYS else redact_secrets(item)
            for key, item in value.items()
        }
    return value
\end{lstlisting}
\end{latin}

این قطعه کوتاه است، اما برای چنین پروژه‌ای اهمیت زیادی دارد. سامانه با گذرواژه، \lr{API Key}، توکن و اطلاعات احراز هویت سروکار دارد. اگر این داده‌ها بدون کنترل وارد پاسخ‌ها یا لاگ‌ها شوند، امنیت کاربر آسیب می‌بیند. جایگزین‌کردن مقدار حساس با \lr{[REDACTED]} کمک می‌کند خروجی‌ها برای بررسی فنی قابل استفاده باشند، اما رازهای کاربر آشکار نشوند.

\section{جمع‌بندی فصل}
پیاده‌سازی پروژه از چند بخش روشن ساخته شده است: فرانت‌اند برای تجربه کاربر، بک‌اند برای قرارداد \lr{API}، \lr{Serializer} برای کنترل ورودی و خروجی، و \lr{Repository} برای کار با داده. کنار هم قرار گرفتن این بخش‌ها باعث می‌شود پروژه از یک نمونه ساده فراتر برود و به یک پلتفرم واقعی اشتراک‌گذاری \lr{API} نزدیک شود.
